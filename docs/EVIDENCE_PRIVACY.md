# Evidence privacy and independent custody

New attachments have two separate representations: a masked review copy and an unchanged original encrypted for an independent custodian. No court private key is generated by, configured on, or returned to the application server. Evidence uploads return HTTP 503 if the custodian public key is missing or invalid; reports without attachments remain available.

## Masked review copies

The submission form can capture JPEG photos, short videos (up to 45 seconds), and microphone recordings (up to two minutes). It requests browser device permission only after a capture button is pressed. Photos request camera access only; video requests camera and microphone; audio requests microphone only. The frontend permits these devices only for its own origin and still blocks geolocation and framing.

Captures remain in browser memory with an explicitly unmasked preview until the reporter chooses **Use this evidence** and submits the report. Discard releases the preview URL; stopping, cancelling, leaving the form, hiding the page, or quick exit stops device tracks. Unsupported browsers and permission refusal leave file upload available. The browser selects a supported WebM/MP4/OGG recording format; WebM audio uses `.weba` so the server processes it as audio. Captures and ordinary uploads share `POST /report-base64`, the same signature validation, masking, and court-sealed storage. There is no direct upload route that bypasses processing. The form enforces five attachments and 8 MiB combined to stay within the base64 request limit. Recording tests use simulated devices; physical iOS/Android device behavior still needs acceptance testing.

FFmpeg reduces image/video detail and blurs the entire frame, including faces. This is deliberately broader than selective face detection. Audio, including the first audio track in a video, is pitch/formant shifted and modulated while preserving spoken content and approximately preserving duration. Extra tracks, subtitles, chapters, and source metadata are omitted. Text is masked; PDFs and processing failures have no downloadable review copy.

Voice alteration is **not guaranteed speaker anonymization**. Names, addresses, accents, context, and other identifiers can remain in speech. Frame blur also cannot guarantee that every contextual clue is removed. Review copies need a human privacy assessment before wider disclosure. No external AI service receives these recordings. These derivatives are review aids, not substitutes for evidentiary examination of originals.

## Custodian setup

An independent court-designated custodian must perform this on their own secured machine, outside the platform administrator's control:

1. Copy `backend/court-custodian.js` and `backend/court-vault.js` to that machine. Node.js is required.
2. Set `SENTINELQ_CUSTODIAN_PASSPHRASE` through a secure local secret mechanism to a unique passphrase of at least 20 characters. Do not put it in source control or shell history.
3. Run `node court-custodian.js init <secure-directory>`.
4. Retain `court-private.pem` and its passphrase independently, with protected backups. Configure restrictive Windows ACLs or equivalent OS permissions on that directory; Unix mode flags alone do not establish Windows ACLs.
5. Give the platform operator **only** `court-public.pem`, verifying its fingerprint through an independent channel.

The operator sets either `SENTINELQ_COURT_PUBLIC_KEY_PATH` to that public PEM file or `SENTINELQ_COURT_PUBLIC_KEY` to its contents (literal `\n` escapes are accepted). The server rejects private PEMs and RSA keys smaller than 3072 bits. Install FFmpeg or set `SENTINELQ_FFMPEG_PATH` to its executable. Restart the server after configuration. Environment-only deployments and isolated tests may use `SENTINELQ_SKIP_ENV_FILE=1`.

Never generate the real custodian private key on the application host, paste it into the admin UI, or configure the custodian passphrase on the server. The key generated by automated tests is ephemeral test data, not a deployment key.

## Court release procedure

1. After receiving a court demand, an admin opens the evidence's **Request original** form and chooses **Export court request**. This creates a request valid for ten minutes, bound to the file and the current authenticated session. Keep that session open.
2. Send the JSON request to the custodian through the approved channel. The custodian independently verifies the court order, requested case, evidence, administrator, and scope. The application does not determine whether an order is genuine or legally sufficient.
3. On the custodian machine, run:

   ```text
   node court-custodian.js release <court-private.pem> <request.json> <court-order-reference> <release.txt>
   ```

4. Transfer the release securely. The admin pastes it into **Signed court release**, records a reason, and selects **Unlock once and download**, or **Authorize and create masked copy** for failed/older derivatives.
5. The server validates the custodian signature, case/file/session binding, expiry, and reason, then consumes the request. A one-use grant expires within 60 seconds. Release tokens expire within five minutes. Concurrent redemption and replay fail. Restart/logout invalidates outstanding requests; logout also clears outstanding grants.

The audit records request, denial, grant, download/reprocessing, administrator, reason, and court-order reference. Neither the release token nor the released file key is logged. Lost/expired requests must be exported and signed again. Session/grant state is in memory: use one Node instance until coordinated state storage is implemented.

## Cryptographic boundary

`SQC1` originals use a random AES-256-GCM key per file. The key is wrapped with RSA-OAEP-SHA256 for the custodian, with the case/artifact context as the OAEP label. The GCM authenticated data contains the envelope, including that context and the public-key fingerprint. The regular `SENTINELQ_STORAGE_KEY` cannot decrypt these originals. Masked derivatives and case fields retain the existing `SQE2` storage encryption.

The custodian signs the request digest, expiry, court reference, and released file key using RSA-PSS-SHA256. A release grants access to **one original**, never the custodian private key. Treat release files as sensitive: their payload contains that original's data key. Expiry restricts API redemption; it cannot revoke plaintext or a file key already received by an authorized admin. A recipient can retain downloaded bytes. Secure handling and retention policy remain necessary.

The upload server necessarily sees plaintext during initial processing. A compromised server could capture future uploads or change its configured public key. This protects stored originals against an admin with database/storage access; it is not end-to-end protection from a malicious application host. Temp files are removed after processing but abrupt crashes, swap, host backups, and forensic recovery require separate secure scratch-storage controls. Independent key custody and external audit anchoring remain operational responsibilities.

## Existing data and key rotation

Existing `SQE2` originals are explicitly labeled **Legacy original: server encryption; custody migration required**. They now require a signed court release at the API, but their old encryption still permits a host with the old storage key to decrypt them. This change does not silently rewrite or delete existing evidence or backups. Arrange a verified, backed-up custody migration before claiming independent encryption protection for old files.

Privacy version 3 blocks older review copies until court-authorized reprocessing. A failed job preserves the protected original and exposes no fallback copy. The cloud storage adapter accepts both encryption formats. The cloud migration utility checks `SQC1` envelope structure/context and verifies copied ciphertext byte-for-byte; it cannot verify original plaintext without a custodian release. The older local security migration leaves `SQC1` envelopes intact.

The current server supports one configured custodian public key. Do not replace it casually: originals sealed to another fingerprint cannot be released with the new key. Keep the old custodian key backups and plan a controlled rewrapping/key-registry migration. Loss of the custodian private key means loss of access to sealed originals.

## Verification

Run `node --test` in `backend` and `node build.js` in `frontend`. Set `SENTINELQ_FFMPEG_PATH` and `SENTINELQ_FFPROBE_PATH` if FFmpeg/FFprobe are outside PATH; without FFmpeg the media test explicitly skips. Tests use isolated temporary stores and cover ciphertext tampering, wrong keys/context, token expiry/signature alteration, session binding, concurrent redemption, replay, RBAC, byte-identical original retrieval, derivative audio/video transformations, and storage-adapter compatibility.

Implementation references: [Node crypto](https://nodejs.org/api/crypto.html), [FFmpeg filters](https://ffmpeg.org/ffmpeg-filters.html), and [Supabase private storage access](https://supabase.com/docs/guides/storage/security/access-control).
